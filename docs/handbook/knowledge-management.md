# Inkling 知识组织与维护规则

状态：当前文档工作约定。更新日期：2026-11-13。

目标是让后续参与者能回答五个问题：产品为什么做、为谁做、为什么这样设计、实际怎么运行、有什么证据说明它有效。文档保留当前可用知识与重要判断的来由，聊天和提交历史用于补充过程。

## 分类目录

目录按知识用途组织。已创建的内容见[知识入口](../README.md)；下面标记“按需创建”的目录在首次产生真实内容时建立。

```text
docs/
  README.md                    当前知识地图与阅读顺序
  handbook/                    知识库组织与维护约定
    knowledge-management.md    本规则
  research/                    行业、用户观察、专题事实与来源
    industry-overview.md
    industry-and-publishing.md
    writing-agent-competitive-analysis.md
    open-source-agent-landscape.md
    framework-evaluation.md
  product/                     稳定原则、价值、需求和交互规范
    design-philosophy.md
    core-value.md
    thinking-partner-product-design.md
    product-design.md          早期综合方案，保留参考
    open-questions.md          有验证入口的开放问题
    features/                  按需创建，每项能力的产品契约
  architecture/                模块、数据、接口与运行机制
    agent-architecture.md      当前架构候选，尚未实现
  decisions/                   产品与技术重大取舍
  engineering/                 按需创建，开发环境、实现约定与贡献流程
  validation/                  按需创建，实验、评测、验收与失败案例
  operations/                  按需创建，部署、迁移、备份、恢复与发布
  retrospectives/              按需创建，里程碑与事故复盘
  diagrams/                    图源、导出文件及相关检查记录
  templates/                   可复用文档模板
```

`docs` 根目录只保留 `README.md`，其他文档必须进入相应分类目录。迁移时同步修正仓库内引用，不在根目录创建旧路径占位文档。目录整理不改写历史结论，由知识入口标明各篇用途与状态。架构方案和实际架构进入 `architecture` 并明确成熟度，候选框架比较归入 `research`。

## 一类知识一个主要维护位置

| 知识类型 | 维护位置 | 需要避免的重复 |
| --- | --- | --- |
| 外部事实和用户观察 | research 与现有专题调研 | 在 PRD、架构和宣传文案中复制竞品表 |
| 原则与价值 | product 的基础文档 | 把不同版本的定位分散在每个 README |
| 用户旅程与范围 | 当前协作设计；后续功能进入 product/features | 在技术方案中另写一套 MVP |
| 重大决定与理由 | decisions | 把“考虑过”写成“已决定”，或只留在聊天里 |
| 计划和已实现的系统结构 | architecture 与现有架构专题，明确状态 | 把候选设计当作实际运行说明 |
| 接口和数据的实际约束 | 版本化 schema、迁移和代码；文档解释语义并链接 | 手抄易失同步的接口字段和代码 |
| 验证证据 | validation | 将测试计划写成测试结论，或仅报告模型主观评分 |
| 运行与发布 | operations | 只记录成功启动，不记录升级、失败与恢复 |
| 经验与后续行动 | retrospectives | 复盘停留在总结，未回写规范和行动 |

每份文档可以用短摘要引用其他文档，但不维护另一份完整副本。既有综合设计中的定位与竞品章节作为当时上下文，后续修改以对应基础文档为主，再检查综合方案是否需要同步。

## 区分事实 假设 决定和实现

文档开头至少写状态、更新日期和适用范围。状态按类型选择：研究可标“初步／已核验至某日／待复核”；方案可标“提案／已接受／部分实现／已实现／被替代”；验证可标“计划／已执行／结论受限”。

“已核验”只说明具体事实与来源相符，不说明产品设计正确。“已接受”说明做出了决定，不说明代码存在。“已实现”应能链接到代码或版本，“已验证”应能链接到方法和结果。

不按文档最新日期自动覆盖所有旧结论。冲突时按主题定位当前决定：作者明确目标约束产品定位；当前范围文档约束 MVP；已接受决策解释取舍；实现记录和代码说明实际行为。计划与实际不一致时，记录偏差并修正，不能静默挑一个当真。

## 轻量追溯方式

```text
研究或观察 → 价值假设 → 功能规范 → 决策与实现 → 验证结果
                                       ↑           ↓
                                    修订规范 ← 复盘
```

这表示知识引用关系，不要求按顺序完成所有工作。重大决定先记录理由；小范围交互调整可直接更新功能规范。

只有需要跨文档追踪时使用 ID：价值采用 V1–V4；决策采用 DEC-0001；功能可采用 F-001；实验可采用 E-001。编号只用于稳定引用，不创建重复登记系统。

例如未来“观点卡”功能的规范链接 V1、V2，说明它如何区分观察和论断；实现后链接代码和提交；验证记录给出作者是否更能解释判断的结果。这个例子是后续记录方式，尚不代表功能已实现。

## 研究来源与版本

影响决定的外部结论应在附近链接原始来源，记录核验日期、产品或依赖版本、事实摘要、证据限制。访谈记录区分原话、观察与研究者解释；未经确认的推断不写成用户需求。

功能、套餐、接口与框架行为在实际购买、接入或冻结版本前复核。较稳定的方法论按出现新证据时更新。可保存的材料保留必要片段与定位；账号凭据和私人日志不写入仓库，用户研究材料按授权脱敏。

## 决策如何演变

值得记录的决定包括产品定位、核心交互、数据模型、运行框架、发布副作用、存储迁移和重要安全边界。记录背景、备选、选择、代价、依据及重新讨论的条件。

已接受的决定可以补充非实质说明；方向改变时创建新记录，并互相链接“替代／被替代”，保留当时理由。未决技术选择标为提案，不因写成 ADR 就视作已定案。

## 每次开发怎样沉淀

开始功能前，写明关联价值、用户场景、范围与验收。实施时链接相关设计和决策，记录实际偏差。完成时补代码入口、测试结果与限制，并更新知识入口中的成熟度。

交互、接口、数据或运行方式发生变化，在同一次变更中更新对应规范。影响部署的变更补迁移和回退说明；发布后保留版本入口与已知问题。测试执行细节优先链接可重复运行的命令和结果，避免仅写“通过”。

里程碑结束时做轻量复盘：原先假设是否成立、发生了什么偏差、哪些设计应保留或修改、谁负责下一步。未发生的工作不用预先制造结论。

## 文档检查

每次变更检查相对链接、标题结构、状态与日期；结论能否区分证据和推断；是否意外重复了另一个权威位置；是否同步相关范围、接口或验证说明。

未来可将本地链接、格式和生成文档一致性检查加入 CI。事实质量和观点正确性仍需要人工审阅，不能以链接有效替代。

## 产品完成时应留下什么

“完成”按明确产品版本或里程碑衡量。届时至少具备：当前价值与范围、关键用户旅程、功能与失败路径、实际架构和数据关系、主要决策及理由、可重复的开发与运行说明、验收与用户价值验证、部署恢复说明，以及已知限制与后续问题。

由这些知识应能还原从问题到运行产品的完整路径，并支持新维护者完成一次修改、验证和发布。文档数量不作为完成度指标。
