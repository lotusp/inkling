# Inkling 产品与技术设计方案

2026-11-13 定位更新：当前产品范围与优先级以[个人技术写作协作设计](thinking-partner-product-design.md)为准，聚焦辅助思考、个人判断与表达。以下早期方案作为能力设计参考，其中完整发布集成等范围需按新 MVP 分期实施。

Inkling 是面向个人中文技术作者的持续写作伙伴：把平时积累的材料和灵感变成有依据、有个人判断的文章，并保留从研究到发布的完整记录。第一版服务个人博客和技术社区；以单人使用、中文为主、中英文资料混合为前提。

产品设计日期：2026-11-11；Agent 技术设计更新：2026-11-12。文章类型和渠道方向已由作者确认；现有博客系统、样文数量、模型预算尚未确定。本文定义拟议产品与实现路线，当前仓库尚未实现这些能力。竞品事实和平台接口依据见[行业调研](../research/industry-and-publishing.md)，运行机制详见[Agent 技术架构](../architecture/agent-architecture.md)。

## 产品定位与核心价值

Inkling 的核心对象是一篇持续演进的文章。对话用于发起任务和讨论取舍，文章项目保存写作简报、资料、灵感、论点、大纲、草稿、修改建议和平台版本。关闭聊天或重启应用后，仍能从上次进度继续。

作者决定写什么、相信什么、想表达什么。Inkling 负责找材料、暴露论证缺口、提出结构、协助表达、检查事实和处理发布格式。最值得长期积累的资产是作者自己的原作、思考及修改偏好。

差异化集中在三处：每个重要事实能回到原文；灵感能追踪到它最终支持的观点和段落；作者的修改能逐步改善下一次协作。这是基于竞品对比提出的方向，尚需通过真实写作验证用户价值。

## 一篇文章如何完成

以“我为什么在个人项目中选择 SQLite”为示例，以下只是交互示意，不代表作者实际使用经历。

| 阶段 | 作者的动作 | Inkling 的工作 | 留下的成果 |
| --- | --- | --- | --- |
| 记录 | 保存一句想法或一段笔记 | 原样保存，建议关联主题；不强制填写分类 | 灵感卡及记录时间 |
| 立题 | 选中几张卡，说“我想写这个” | 提出受众、核心问题、立场和范围；只追问真正影响方向的信息 | 可编辑写作简报 |
| 研究 | 指定材料或要求补充资料 | 先查私人资料，再搜索官方文档、原始文章与反例 | 研究摘要、证据卡、待核实问题 |
| 构思 | 讨论想强调的判断 | 给出两种结构，展示论点、依据、反例与段落目的 | 论点表及大纲 |
| 起草 | 选择分节协作或整篇草稿 | 按所选风格生成候选稿，保留引用和待补信息 | 新草稿版本 |
| 编辑 | 接受、拒绝或手改某段 | 针对局部给出修改建议和理由，检查上下文连贯性 | 差异记录及反馈 |
| 定稿 | 审阅事实和表达 | 标注引用不匹配、过期结论、没有依据的数字和重复内容 | 审阅结果及定稿版本 |
| 发布 | 检查目标渠道预览并确认公开 | 适配图片、代码、标题、标签，执行发布并核验结果 | 平台链接及发布记录 |
| 复用 | 开始下一篇 | 推荐相关旧材料；提出可加入风格库的修改偏好 | 可复用资料与经确认的偏好 |

任务允许跳转：已有草稿可直接编辑；只想记录灵感时不启动研究；只要大纲时不自动生成全文。补研究可以与编辑同时进行，但研究结果先成为建议，不覆盖正在编辑的正文。

## 六项核心能力

### 灵感收件箱

第一版支持文本、URL、Markdown 文件和选中文本粘贴；入口随时可用，先保存后整理。每张卡保留原始内容、来源、时间、作者附注和关联文章，自动标签可修改。

明确区分“我的想法”“原文摘录”“AI 建议”。模型推荐的观点不会自动归入作者立场。语音、截图识别、浏览器扩展和移动端分享入口放在后续版本，先验证灵感是否真能在写作时被找回。

### 可追溯的资料研究

研究任务先产生待回答问题及检索范围，再搜索、去重、抽取与整理。每份资料保存标题、作者或机构、URL、发布时间、抓取时间、内容摘要、内容哈希和解析状态。能合法保存的正文生成快照；受限材料保留元数据、允许保存的片段和用户批注。

快照分为 `full / excerpt / metadata_only`，分别表示全文、允许保留的片段和仅元数据。证据卡必须包含原文片段、快照 ID、定位信息、适用版本或时间，以及它支持或反驳的论断；片段快照只证明已保存范围内的内容。仅有元数据的材料不能标记为“原文已核验”。网页优先保留标题路径和文本偏移，PDF 保留页码。搜索结果摘要只用于发现资料，不能直接充当已经读过的证据。

事实检查分两层：程序验证引用对象存在、片段能定位；模型辅助判断原文是否支持论断。后者仍可能出错，因此显示“有支持”“部分支持”“有冲突”“待核实”，并让作者打开原文判断，不给伪精确的可信度百分比。

来源更新不静默替换旧证据。新快照触发相关论断复核；数字、产品能力和接口行为在定稿前检查时效性。资料不足时，输出明确缺口或保留占位，而不是补造结论。

### 思路与论证组织

每个文章项目有一份短简报：目标读者、要回答的问题、核心观点、预期读者收获、篇幅、体裁与排除范围。Inkling 对缺失项提出默认值，作者随时更改。

大纲中的每节包含“本节要说什么、为什么需要它、使用哪些证据、有哪些反例、缺什么”。第一版用可排序的大纲和论点卡实现，不引入复杂的无限画布。对需要个人判断的地方，给出可比较的选项，并说明各自取舍。

### 作者风格与长期记忆

初次使用建议导入 5–10 篇自己认可的原作；这只是起步建议，没有样文也能通过偏好设置和一次试写开始。按教程、技术复盘、观点文章分别标记样本，排除大段引用、他人代写及尚未认可的 AI 文本。

作者上下文由四部分组成，其中作者经历与观点是独立事实记忆，不随风格切换而改变：

| 部分 | 保存内容 | 用途 |
| --- | --- | --- |
| 表达规则 | 语气、句长、段落节奏、标题习惯、术语翻译、代码解释方式、禁用套话 | 形成可编辑的写作约束 |
| 原作样本 | 有来源的代表性段落，按体裁和表达任务标记 | 起草时检索少量相关例子 |
| 作者事实与观点 | 经作者确认的经历、立场，以及适用范围 | 防止生成不存在的“我曾经……” |
| 编辑偏好 | 修改前后、接受或拒绝、理由、仅本篇还是长期适用 | 改善后续编辑建议 |

导入后先展示风格卡和一段试写，让作者修正，再建立版本。每次起草组合“任务要求＋文章事实＋体裁风格＋少量原作示例”，不把整个样文库塞入上下文。

修改反馈先成为本篇偏好。多次出现的模式可被推荐为长期规则，但只有作者确认后生效；支持查看依据和撤回。P0 只启用一个默认风格，样本预留文类标记；P1 再增加多个风格的选择、规则覆盖和分别评估。生成内容即使发布，也不会自动回灌为原作样本，避免风格逐步被模型自己的表达替代。

第一版采用规则与样本检索；待积累足够、质量可控的编辑数据并证明现有方案不足后，再评估微调。

### 可审阅的写作与编辑

提供三个入口：讨论思路、按大纲起草、修改选中段落。默认在文章里工作，右侧对话可引用当前选区、某条证据或某张灵感卡。

AI 输出保存为候选版本或修改补丁，作者可逐项接受、拒绝或自行修改。补丁包含目标段落 ID、基线版本、修改内容和原因。基线过期时提示冲突，不覆盖作者刚写的文字。代码块、公式、引用、链接和图片作为结构化内容处理。

审阅建议分为事实、论证、风格和技术格式四类，允许单独运行。事实审阅不能为了语气流畅而改写技术结论；风格审阅不得凭空新增作者经历。代码示例标注是否实际运行过，未执行时不声称验证通过。

### 发布与文章复用

一篇文章保留统一主稿及多个平台衍生稿。平台只改变自己需要的字段和格式，不能反向污染主稿。正文、图片、标题和标签的转换应有预览，代码、公式或图表无法保真时给出明确的替代方式。

第一版提供 Markdown、HTML、图片资源和 front matter 导出，再连接作者现有的一个博客系统。若已有 Git 博客，生成提交或 PR 并跟踪部署；若使用 WordPress 或 Ghost，先创建草稿，再公开发布。DEV、Hashnode 及国内社区按实际需求扩展，详见[平台评估](../research/industry-and-publishing.md#发布平台与接入路线)。

自动保存、资料整理和候选稿生成可按作者设置自动执行。公开发布需要对具体平台版本、账号和可见性作出明确确认；确认前直接展示成果，避免反复询问抽象许可。远端删文、覆盖已发布文章和订阅推送独立处理。

## 工作台交互

桌面工作台采用三栏：左侧是灵感、文章项目和资料库；中央是当前文章及大纲；右侧在证据、AI 对话、修改建议之间切换。把选区发送给 Agent 时明确显示上下文范围。

文章顶部显示当前阶段、保存状态、待核实事项和下一步建议。研究过程中可以继续写作；任务面板显示正在查什么、已找到什么、是否遇到限制，并允许取消。每条引用能打开原文定位，每条修改能展开理由，每个发布结果能回到对应正文版本。

常用指令示例：

- “先保存这段灵感，关联到数据库选型，不用展开。”
- “把我关于 SQLite 的笔记找出来，指出还缺哪些资料。”
- “列两种文章结构，让读者先看到实际问题。”
- “按我的技术复盘风格重写开头，保留这个例子。”
- “检查第三节的版本号和引用，只提出修改建议。”
- “把定稿生成博客草稿，展示图片和代码的渲染效果。”

## 技术架构

采用 TypeScript 模块化单体：一个写作工作台、一个应用服务、一个可恢复的后台任务执行器。Research、Outline、Write、Review 是同一工作流中的能力模块，各自拥有输入输出约定；需要时可并行检索不同问题。初期不把它们拆成独立服务。

可交互[产品架构图](../diagrams/inkling-architecture.html)展示组件与权限边界，[Agent 内部运行图](../diagrams/inkling-agent-runtime.html)展示任务调度与执行关系。详细技术选型、循环控制、恢复、Skills、MCP、subagent、会话和记忆以[Agent 技术架构](../architecture/agent-architecture.md)为准。

| 层 | 第一版建议 | 选择原因及边界 |
| --- | --- | --- |
| 界面 | React、Vite、shadcn/ui、Tailwind CSS，Tiptap 编辑器 | 支持段落、代码和引用节点；建议审阅的业务逻辑自行实现，商业扩展另行评估 |
| 应用服务 | Node.js、TypeScript、Fastify；LangGraph.js 统一编排 | 前后端共享数据类型；显式工作流与有限循环由同一个运行时管理 |
| 持久化 | SQLite、Drizzle 保存业务状态和文章版本；文件目录存附件 | 图检查点独立存储；先服务单用户，未来多实例部署再评估 PostgreSQL 与对象存储 |
| 检索 | 标签与字段过滤、中文检索处理、全文检索 | 先做可靠查找，再按实际召回问题引入向量检索 |
| 模型接入 | 统一 ModelGateway，支持更换提供方 | 封装单次调用、结构化输出、流式结果与用量；不再开启第二套 Agent loop |
| 任务执行 | 持久化 Job 表、常驻 Worker、租约和取消；LangGraph 检查点 | 队列负责调度，图负责步骤；恢复时复用已提交成果，不无条件重放外部写入 |
| 工具与方法 | 内置 Skills、原生工具、MCP Client 与平台适配器 | 方法和权限分开；所有工具经过统一参数、预算、权限和副作用校验 |

编辑器以结构化 JSON 为主内容，Markdown 和 HTML 是导出格式，避免多种格式同时成为事实来源。Tiptap 官方也建议以 JSON 持久化，便于解析及外部修改。[Tiptap 文档](https://tiptap.dev/docs/editor/core-concepts/persistence)

中文检索需要单独验收。SQLite FTS5 的 trigram 支持子串检索，但全文查询对不足三个 Unicode 字符的片段不匹配；因此短中文词需要中文分词后的索引或受范围限制的匹配兜底，不能把默认英文分词的结果当成中文检索质量。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)

本地优先指业务内容保存在作者控制的存储中；调用远程模型、网页搜索或发布平台时仍会发送必要内容。界面应展示可发送范围，提供按项目关闭外部调用的选项。本地服务只绑定回环地址，凭据进入系统密钥存储或加密凭据库，不写入文章、提示词和日志。

## 数据与记忆边界

| 对象 | 关键字段与职责 |
| --- | --- |
| Idea | 原文、来源类型、时间、标签、关联文章；区分作者输入与 AI 建议 |
| Source 与 SourceSnapshot | 来源元数据、抓取时间、正文哈希、快照类型及保存范围、解析状态、访问限制 |
| Evidence | 来源快照、原文片段、定位、适用时间或版本 |
| Claim | 论断、作者观点或外部事实、支持与反驳证据、核验状态 |
| ClaimOccurrence 与 Verification | 论断在文章版本中的节点 ID 与文本哈希；核验绑定论断文本哈希、证据快照 ID 和检查时间 |
| Article 与 ArticleRevision | 简报、大纲、当前版本指针；每个保存版本记录内容、父版本和生成方式 |
| StyleProfile 与 StyleExample | 风格规则、样文、文类、版本、确认状态 |
| AuthorMemory | 作者经历与立场、依据、确认状态、时间和适用范围；独立于表达风格 |
| EditFeedback | 补丁、用户动作、修改理由、适用范围；不自动升级为长期记忆 |
| Session、Run 与 Job | 会话消息、单次任务、输入版本、状态、调度租约、预算、错误和取消状态 |
| ToolOperation 与图检查点 | 操作意图及结果负责业务去重；图快照负责执行恢复，不能替代文章和发布记录 |
| PublicationVariant | 主稿版本、平台格式、图片映射、转换结果及内容哈希 |
| Approval 与 PublishJob | 作者授权的目标账号、平台、版本、公开动作；执行状态与审计记录 |
| Publication | 远程 ID、链接、远端版本、最后同步哈希及上线核验状态 |

引用使用稳定 ID，不依靠会随编辑变化的“第 3 段”定位。每处论断绑定具体文章版本、节点 ID 和文本哈希；论断文字、适用条件或证据快照变化时，原核验结果失效并标记为需要复核。私人原作、外部研究材料、风格示例分别检索；作者声明的优先级高于自动推断。

删除资料时同步删除索引与派生副本，并明确提示已有文章的引用将失去可回看的原文；保留引用元数据还是一并删除由作者决定。支持导出文章、资料元数据、风格规则和版本记录，避免资产被困在应用中。

## Agent 执行与工具契约

文章阶段为 `idea → brief → research → outline → drafting → review → ready`，允许回退与跳转；单次 Run 使用 `queued / running / waiting_user / paused / succeeded / failed / cancelled / limit_reached / needs_reconciliation`。文章阶段不被某次工具失败直接改写，会话也不等同于一次 Run。

执行步骤固定为：读取当前文章版本与任务 → 选择相关上下文 → 提出有限步骤 → 调用允许的工具 → 校验输出 → 保存检查点 → 生成候选成果。每次运行记录输入版本、模型配置、提示词版本和检索证据 ID，便于重现问题。

建议的内部工具约定：

| 工具 | 输入重点 | 输出与副作用 |
| --- | --- | --- |
| `capture_idea` | 原始内容、来源与可选关联 | 新灵感 ID；保留原文 |
| `search_library` | 查询、资料范围、过滤条件 | 带定位的候选材料；只读 |
| `research_topic` | 问题、来源策略、搜索及费用上限 | 证据与待解决问题；不直接改稿 |
| `propose_outline` | 简报、论点与证据 ID | 大纲候选版本 |
| `draft_section` | 基线版本、章节、风格版本、证据 ID | 新稿或补丁，不覆盖当前稿 |
| `review_article` | 指定版本、审阅类别 | 可定位的问题及建议 |
| `prepare_publication` | 定稿版本、渠道及账号 | 平台预览、转换问题、内容哈希 |
| `publish_approved_variant` | 发布任务 ID 与有效授权引用 | 由服务端校验并执行，返回状态与远程标识 |

模型不能自行产生有效发布授权。应用服务在作者确认后写入 Approval，并检查执行动作是否匹配。平台凭据只在适配器中使用。网页、PDF 和工具输出作为不可信资料处理，其中的命令、链接或提示不改变系统权限，也不能触发发布工具。

设置每篇文章的检索次数、抓取页数、上下文大小、运行时间和费用上限；耗尽时保存已有成果并提示缺口。临时错误有限重试，权限错误直接返回，结构化输出错误最多进行有限修复。成本按实际输入输出用量、检索、解析和重试分项记录，不预设未经测量的单篇价格。

## 发布可靠性

平台适配器声明是否支持草稿、更新、图片上传、计划发布、canonical、公式和图表；未知能力按未启用处理。一个账号的权限变化不能影响其他账号或主稿。

发布状态为 `prepared → uploading → draft_created → awaiting_approval → publishing → published`；另设 `failed / unknown / needs_review`。不支持远端草稿的平台以本地预览代替 `draft_created`，统一接口不强迫所有平台具备相同能力。准备草稿所需的外部写入受该账号的已授予权限控制。

一次公开授权绑定文章版本、平台衍生稿哈希、账号、可见性、发布时间和图片清单。编辑任何实际公开内容后，旧授权失效。发布前检查远端草稿版本，避免覆盖平台上的手工修改；发生冲突时保留两个版本供审阅。

为每次具体发布意图保存稳定 ID，并用它与操作步骤作为去重键；确认对象包含平台衍生稿、账号、动作及实际公开内容的哈希。重复确认复用原意图，重启或图重放复用已执行操作；新发布请求还需检查该平台已有的远端文章关系，不能仅靠主稿版本判断是否重复。数据库约束、任务锁和 outbox 防止同一操作被本地重复调度，但不宣称因此拥有跨平台的恰好一次语义。网络超时可能发生在远端已成功之后，必须进入 `unknown`，先按 remote ID、slug 或平台返回记录核对，再决定是否重试；无法核对时交给作者处理。

Git 渠道的提交、合并、部署和页面可访问是不同事件。只有部署成功并检查目标页面后才显示“已上线”；如果平台存在审核流程，显示“已提交审核”，不冒充发布完成。某个平台失败只影响该平台任务，其他平台结果保持可见。

## 开发阶段与验收

### P0 完成第一篇真实文章

按依赖顺序做四个可独立验收的里程碑：

1. **捕获与编辑**：灵感收件箱、文章项目、结构化编辑、自动保存、不可变版本、Markdown 导出。验收为关闭重启后内容完整，任一旧稿可恢复。
2. **资料与论证**：URL 与文本资料导入、检索、证据卡、论点大纲、受预算限制的联网研究。验收为重要论断可回看原文，解析失败和证据缺口明确可见。
3. **风格与审阅**：样文导入、风格卡、分节起草、局部修改、差异审阅、反馈范围。验收为编辑冲突不丢字，原作与生成稿分离，作者能修正风格规则。
4. **一个发布闭环**：完整导出及作者现有博客的一种适配器、平台预览、版本授权、失败恢复。验收为从一条灵感生成文章、完成真实发布并拿到经过核验的链接。

P0 暂不纳入实时多人协作、移动端独立应用、全平台自动发布、自主日更、模型微调和复杂知识图谱。扫描 PDF/OCR、大文件与音视频处理在验证主要资料类型后安排。

### P1 改善日常使用

根据 P0 使用记录增加浏览器剪藏、Readwise 或 Obsidian 导入、PDF/OCR、语音灵感、语义检索、多个文类风格、第二个发布适配器和中文社区排版模板。优先解决作者每周反复遇到的阻力。

### P2 扩展复用与分发

支持系列文章、旧文更新、跨文章术语一致性、中英版本、按渠道改编和发布后复盘。阅读量等外部数据只能作为选题反馈之一，不自动改变作者立场或风格。

## 质量评估与必须通过的场景

从作者同意使用的真实素材中建立评估集：5–10 篇风格样本，另留至少 3 篇原作或 3 个新题目作评估，不把评估原文放进提示词。比较同模型的普通提示、风格规则、规则加样例三种方式，让作者盲评“像不像我、观点是否准确、需要改多少”。

首轮先记录人工写作基线和前 5 篇 Inkling 文章：达到可发布质量所需的作者活跃时间、重大事实修正数、风格评分、单篇实际成本。用相近文类比较，不能用生成字数或 AI 自评分代替成效。

| 必测场景 | 验收要求 |
| --- | --- |
| 引用存在但不支持结论 | 能指出不匹配并打开原文，不能只检查 URL 可访问 |
| 两个资料结论冲突 | 保留分歧与适用条件，不默默挑一个作为事实 |
| 原文更新或无法访问 | 显示快照时间、复核需求和抓取失败 |
| 中文短词与中英混合查询 | 在固定语料上命中作者已标注的目标资料 |
| 用户与 AI 同时改同一段 | 检测基线冲突，不覆盖人工输入 |
| 拒绝修改或移除样文 | 不产生长期偏好污染，后续检索不再使用移除样本 |
| 无依据的作者经历 | 保留待补信息，不能编造第一人称经历 |
| 网页包含恶意工具指令 | 只能进入资料内容，不能改变工具权限或泄露凭据 |
| 发布请求超时或重复点击 | 不盲目新建重复文章，保留未知状态并核对远端 |
| 批准后正文或图片变化 | 旧授权失效，不能发布未经检查的新版 |
| 远端内容被手工修改 | 检测冲突，不覆盖修改 |
| 图片、代码、公式、图表不兼容 | 在预览中显式指出转换结果，无静默丢失 |
| 重启、取消、预算耗尽 | 保存已完成步骤，停止后续动作，可明确恢复 |

用户试写中的硬性目标为：没有未经授权的公开发布；重要可核验论断都有原文支持或明确的待核实标记；版本恢复不丢失内容。模型审阅只能辅助实现这些目标，发布前仍需作者审阅重大问题。

## 开发前需要补齐的配置

现有博客系统决定第一个适配器；作者愿意提供的原作决定初始风格库；模型供应商、网络可用性和预算决定模型网关的默认配置。这些不影响先实现捕获、文章编辑、版本和导出。建议第一条开发任务就是用一份真实材料跑通这个基础工作台，再逐步接入研究、风格和发布。
