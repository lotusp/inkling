# Inkling 设计哲学

状态：当前设计原则；产品实现尚未验证。更新日期：2026-11-13。依据：作者明确提出以真正思考、整理和表达个人洞见为目标，详见[定位决策](../decisions/0001-thinking-partner-positioning.md)。

Inkling 帮助作者通过写作形成理解。产品应尊重思考的节奏、作者的判断和表达意图，让资料、讨论与文章之间的关系更清楚。

## 以问题和理解为起点

作者可以从一句想法、一段经历、一份材料或已有草稿开始，不必先确定标题和结论。系统允许保留未知、相互冲突的解释与未成文的探索。

设计约束：提供记录、讨论和继续草稿的入口；大纲可以修改或从草稿中反向提取；不得把所有使用路径强制推进到全文生成。

检验问题：一次协作即使没有产出文章，是否留下了更明确的问题、边界或下一步？

## 作者拥有判断权和表达权

模型可以提出解释、挑战观点和协助表达。作者决定哪些内容代表自己的立场。作者确认某个观点，不等于该观点已经被事实验证。

设计约束：区分作者观察、外部摘录、模型建议和作者确认的判断；改写展示差异；不静默加入个人经历或新立场；拒绝建议和恢复旧稿必须容易。

检验问题：作者能否解释最终观点为何成立，指出哪些表达是自己接受的，撤回一次不满意的修改？

## 通过讨论暴露缺口

协作既可以帮助展开想法，也可以指出反例和过度概括。追问应围绕当前问题，避免机械提问、无条件附和或为了反对而反对。

设计约束：默认一次一个主要追问，支持跳过、暂停和调整审阅强度；几轮讨论后总结已知与未知；已有足够上下文时直接推进，不重复询问。

检验问题：每次打断是否带来值得作者处理的信息？

## 保留技术判断的适用条件

技术观点通常依赖版本、环境、规模、约束和证据范围。经历可以支持个人判断，但一次经历不能自动推导普遍结论。

设计约束：关键论断可关联原文、代码或实验材料及条件；缺少依据时保留缺口或建议收窄；修改正文后重新检查相关引用；引用存在与引用支持论断分开验证。

检验问题：读者能否理解这个结论在何种情况下可能不成立？

## 减少事务负担并保留思考投入

查找、搬运、重复整理和格式修复可以被自动化。比较解释、形成判断和承担表达需要作者参与。总时长降低并非所有任务的唯一目标。

设计约束：先保存后整理；研究有可调整的预算和停止条件；自动化产出可检查的结果；不用强制分类或复杂知识建模阻挡输入。

检验问题：工具减少了哪些低价值操作，又增加了多少新的管理工作？

## 结构服务当前思考

观点卡、大纲和资料关系应该帮助作者，而不能成为另一份需要维护的项目。输入可以自由，结构可以逐步产生并随时修改。

设计约束：第一版使用简单卡片和可排序大纲；ontology 先表达问题、观察、论断、证据、反例、条件和段落的关系；不要求作者理解本体术语或操作图数据库。

检验问题：删除一个结构字段，会损失实际能力还是只损失形式完整性？

## 长期记忆可以修正

作者会改变观点，风格也因文章类型而变。记忆应帮助找回理解，允许变化，不把过去的一次选择永久固化。

设计约束：经验、观点、风格偏好与来源分开保存；长期更新经作者确认；支持修改、删除和导出；保留观点变化的原因；未采纳的模型生成内容不自动作为作者原作。

检验问题：新证据能否帮助修正旧认识，而不被旧记忆强行覆盖？

## 阶段选择与原则冲突

| 冲突 | 当前处理方式 |
| --- | --- |
| 快速生成与作者意图 | 可以按请求生成草稿，但清楚保留候选性质和未知项，由作者决定采纳 |
| 深入研究与注意力预算 | 先处理最影响判断的问题，到达预算后交付部分结果和缺口 |
| 可追溯与记录成本 | 默认保存已有来源信息；只要求作者补充影响判断的重要背景 |
| 风格学习与表达变化 | 使用文章级偏好，长期偏好可调整，保留例外 |
| 批评帮助与被打断 | 提供主动调用、暂停与强度选择，集中呈现高影响问题 |

功能评审应说明服务了哪条原则，以及可能损害哪条原则。重大取舍进入决策记录；实际效果进入验证记录，不能只凭设计意图认定成功。
