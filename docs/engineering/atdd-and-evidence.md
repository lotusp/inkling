# ATDD 与验证证据

更新日期：2026-11-16。状态：测试与验证约定，正式应用命令在首条工程 change 落地。

## 验收先行

验收来自作者任务、异常恢复和不应发生的副作用。Delta Spec 用 Requirement 与 Given/When/Then 描述可观察行为；acceptance.md 记录场景 ID、测试层、夹具、入口、断言与证据位置。任务按场景切片，不按“全部后端 → 全部前端 → 最后补测试”拆分。

每个场景选择能证明契约的最低可靠层；重要 UI 闭环仍须经过 UI。组件测试可以补交互细节，不能代替保存或发布的端到端语义。无数据库不代表所有测试都必须 E2E。

| 层级 | 用途 | 是否必须真实 |
| --- | --- | --- |
| 单元 | 版本比较、状态转换、预算、格式转换 | 确定性逻辑；clock/ID 可控 |
| 用例/存储集成 | 保存、并发冲突、恢复、任务生命周期 | 正式选定存储，隔离临时工作空间 |
| API 契约 | 参数、错误、幂等、取消、SSE | 真实服务与用例；外部模型/网络用可控替身 |
| UI E2E | 编辑与 Chat、接受建议、版本恢复、发布确认 | 真实 UI → 服务；外部副作用使用测试目标 |
| 真实适配器冒烟 | 模型调用、博客草稿/发布/更新 | 已授权的真实服务；缺环境标未执行 |
| Agent 效果评测 | 中文表达、原意保留、证据适配、追问价值 | 固定数据与模型版本，保留人工抽查和不确定性 |

## Red → Green 的证据

新增行为：先编写或补充对应验收测试，运行并保存有效失败，再实现并验证同一场景通过。已有行为 baseline-pass 要记录验证基线和原因；不反向制造失败。配置/文档 change 的验证可以是结构或命令检查，不要求没有意义的业务单元测试。

测试断言必须对应需求，禁止只验证 mock 被调用、复制实现算法或机械快照整个页面。失败用例覆盖版本冲突、取消迟到结果、未确认记忆、未确认发布等与 change 相关的边界。性能、恢复与隐私约束进入范围时，直接设计相关验证，不需要额外的签署会议。

重构后运行受影响验收和回归，G2 运行项目已声明的必需检查。前端变化补浏览器观察；中文输入法、休眠和真实发布等自动化无法充分覆盖时，保留简短操作记录，不能标为已自动验证。

## 模型质量单独评价

确定性用例保证“旧建议不能覆盖正文”“取消后不产生新副作用”；模型效果评价“是否保留原意、依据是否支持论断”。两者分别报告。使用 mock 模型可让默认 CI 稳定，真实模型回归按受影响的 prompts、Skills、模型或检索路径执行。

评测记录模型/提供方/参数、Skill 内容 hash、数据版本、输入范围、输出、调用次数、延迟和成本。数据包含正例、反例与资料中的恶意指令；引用核验检查可定位原文，不仅检查输出包含 URL。判分标准在看结果前确定，不为当前输出临时调线；LLM judge 作为辅助，不是作者洞见的最终裁判。

默认 CI 不读取个人稿件或外部账号密钥；真实服务测试单独显式启动。没有建立真实基准前不设武断质量百分比，也不宣称几个样例代表整体模型质量。

## 机器可读证据

`verification.md` 解释结果和限制；`evidence.json` 是精简索引。日志使用 change 内的相对路径，精简到可检查的命令、退出码和断言；脱敏后入库，巨型 trace 与私人样文不入库。以下仅为字段示例，不是已经通过的记录：

```json
{
  "schemaVersion": 1,
  "changeId": "example-change",
  "result": "passed",
  "subject": [
    { "path": "@change/specs/article-save/spec.md", "sha256": "64位实际摘要" },
    { "path": "apps/server/src/article-save.ts", "sha256": "64位实际摘要" }
  ],
  "checks": [
    { "id": "acceptance", "command": "仓库中实际存在的验收命令", "status": "passed", "exitCode": 0, "log": "evidence/acceptance.log" }
  ],
  "scenarios": [
    { "id": "ARTICLE-SAVE-001", "status": "passed", "checkIds": ["acceptance"] }
  ]
}
```

`subject` 至少包含所有 delta spec；另外必须覆盖该 change 相关代码、测试、配置、lockfile、提示词/Skills 和夹具。`@change/` 相对当前或归档后的 change 目录解析，其他路径相对仓库根目录，路径必须在仓库内。不要把 evidence.json 自己放入指纹造成循环。

脚本复算列出的 hash，缺日志、非零退出、未完成任务、缺场景映射或被测文件变动会阻断 verify 结构检查。它不能自动证明 subject 列表覆盖所有应测文件；执行者必须结合 Git diff 核对，CI 后续应自动生成覆盖清单。时间、真实工具版本、有效 Red 或 baseline-pass、审阅记录及风险在 verification.md 中保留。

`result: passed` 只能在实际必要检查通过后填写。检查未运行或仍有 blocker 时保留 `blocked` / `failed`，不要为了让脚本成功伪造 JSON。手工验收同样要有真实操作记录，并在 command 说明手工流程。

## 合入与归档验证

归档后先核对每条 delta 在 Living Spec 的效果，再运行所有 specs 与 archive 的 strict 校验、文档链接和结构检查。ADDED/RENAMED 的目标应存在，REMOVED 应消失，MODIFIED 保留未改变的场景，不能只看“文件已移动”。

若 Git 合并带来冲突解决或其他代码变化，原证据可能失效，必须重跑受影响检查；普通 fast-forward 且被测输入未变可引用原证据。G3 记录合入提交与归档路径；该记录可以留在最终交付说明或 PR，不为写入自身 SHA 反复制造提交。

CI 的建议必需集合是：安装锁定依赖、OpenSpec strict 校验、串行/证据结构检查、格式/lint、类型与架构边界、单元/集成、受影响 E2E、构建。首条工程 change 才创建真实工作流；任何必需步骤不存在或没有发现测试时不能绿色放行。
